### 0.4 原始红线（计划阶段的历史约束，不等同于当前实现）

> 以下保留的是**计划编写时**的防错约束。MPU 强序、QSPI 引脚、热代码不放 XIP、硬件等待超时等仍是重要约束；
> 但第 4 条关于异步双缓冲的理由已被当前 C 工程真机验证推翻，见下文特别标记及 `E:/ymgui-h743/docs/MEMORY_ARCHIVE.md` §九–十。

1. **FMC 区的 MPU 属性必须与 `stm32-tetris` 完全相同**：  
   `RASR = ENABLE | SIZE=25 | TEX=0 | C=0 | B=0 | AP=0b011 | XN=1`，`CTRL = ENABLE | PRIVDEFENA`。  
   **严禁**改成 Device（`B=1`）或 Normal（`C=1`）——本项目历史上正是因为该区域被当作  
   可缓冲/可重排序内存而导致**整屏花屏**，改成强序才修复。
2. **不改 QSPI 片选与引脚**（PB10 = NCS 必须自己配成 AF9；详见 §6.2）。
3. **热代码与栈/堆不放 XIP 区**（LCD 写循环、中断服务、`GY_malloc` 的堆）。
4. ~~**不用 `buf2` 异步双缓冲**：FMC SRAM 模式没有传输完成信号，无法重叠。~~ **历史假设，已被当前 C 工程证伪。**
   H743 的 DMA1 MEM2MEM 传输有自身 TC 标志，不需要面板提供完成信号；当前工程用 DMA1_Stream1 + SRAM3 第二块 band buffer，
   在 FMC 访问前先 drain 上一笔 DMA 后实现了双缓冲，面板 GRAM 高频重绘回读为 0 失配。当前性能、开关和花屏修复见
   `E:/ymgui-h743/README.md` 的“第 6 项 + 第 7a 项”与 `E:/ymgui-h743/docs/MEMORY_ARCHIVE.md` §九–十。
5. **所有硬件等待必须带超时上限**，失败返回错误，不允许 `while(flag);` 死等。
6. **除阶段 0 外不得修改 `E:\stm32-tetris`**。
7. **不新增对外驱动引脚**；确需新增连接时先估算电流量级并写进注释。

## 1. 硬件事实（已实测，直接采信，不要重新推导）

### 1.1 屏幕

| 项        | 值                                                                    |
| -------- | -------------------------------------------------------------------- |
| 面板       | 3.5" 8080 并口 MCU 屏，驱动 IC **ST7796**，**竖屏 320×480**                   |
| 像素格式     | 必须 **RGB565**（`COLMOD = 0x55`）                                       |
| 地址映射     | `LCD_REG = 0x600F_FFFE`（RS=0，写命令）/ `LCD_RAM = 0x6010_0000`（RS=1，写数据） |
| 控制脚      | `PA8` = RST，`PB1` = 背光（**主机控制**）                                     |
| FMC 内核时钟 | **HCLK3 = 200 MHz**，一周期 5 ns（实测 `RCC_D1CFGR @0x5802_4418 = 0x48`）    |

**FMC 引脚是非标准乱序映射，绝不能套用手册的标准 FMC 分配**：

```text
D0  D1       -> PD14 PD15      NWE -> PD5      NE1 -> PD7
D2  D3       -> PD0  PD1       NOE -> PD4      RS(A19) -> PE3
D4  .. D12   -> PE7  .. PE15
D13 D14 D15  -> PD8  PD9 PD10
全部 AF12，且 OSPEEDR 必须显式设 VeryHigh
```

⚠ `PD11 / PD12 / PD13` **不在 FMC 数据线上**（它们是 QSPI），别按手册标准映射接。

### 1.2 外部 Flash

| 项  | 值                                                                |
| -- | ---------------------------------------------------------------- |
| 芯片 | **W25Q128**，16 MB，JEDEC ID `0xEF4018`，命令 `0x90` 读回 `0xEF17`      |
| 引脚 | CLK=PB2，**NCS=PB10**，IO0=**PD11**、IO1=**PD12**、**IO2=PE2**、**IO3=PD13**（全 AF9） |
| 速度 | 预分频 1 ⇒ **100 MHz**（芯片上限 133 MHz），Mode 3，CSHT=5，FSIZE=23         |

> ⚠ **2026-10-03 更正**：本节原先写的是 `IO0/IO1/IO2/IO3 = PD11/PD12/PD13/PE2`
> （把 IO2/IO3 写反了）。**AF9 的引脚↔信号映射由芯片固定，不能靠软件调换**，
> 所以只能有一组是对的。实测 `IO2 = PE2、IO3 = PD13`（与厂商 `qspi.h` 一致）：
> `0xEB` 四线读把 IO0..IO3 分别当 bit0..bit3，若 IO2/IO3 接反则读回每字节的
> bit2/bit3 会互换、数据必错；实测 256 块 × 256 B **失配为 0**，证明该归属正确
> （同时验证了 IO0=PD11、IO1=PD12）。

### 1.3 触摸

| 信号  | **本机实测引脚**           |
| --- | -------------------- |
| SCL | PB11                 |
| SDA | **PB14**（开漏，可回读 IDR） |
| RST | PB12                 |
| INT | PB13                 |

⚠ **不要照抄 V1.2 资料包的 `ctiic.h`**（那里是 SDA=PB12 / RST=PB13 / INT=PC4），  
本机是 V1.1 板。**唯一判据**：按上表能读出产品 ID ASCII `1158`；换错一根收不到 ACK。

### 1.4 现有引脚占用（新增外设前先查）

FMC：PD0/1/4/5/7/8/9/10/14/15、PE3、PE7…PE15；QSPI：PB2/PB10/PD11/12/13/PE2；  
触摸：PB11/12/13/14；屏控制：PA8/PB1；按键：PA0/PA1；SWD：PA13/PA14。

**完全空闲**：PA2…PA7、PA9…PA12、PA15、PB0、PB3…PB9、PB15、PC0…PC15、PD2/PD3/PD6、  
PE0/PE1/PE4/PE5/PE6。

## 2. 阶段 0：FMC 写时序收紧（**唯一允许改 `stm32-tetris` 的阶段**）

### 2.1 为什么只做这一项

> ✅ **本阶段已于 2026-10-03 执行完毕**，完整数据与证据见 **`docs/FMC_WRITE_TIMING_SCAN.md`**。
> 下面这一段保留原始预估，并附实测更正。

帧率只由“把像素写进面板的有效速率”决定。

**实测更正**：基线 `15/15` 的真实每像素耗时是 **154.97 ns/px**（不是预估的 443 ns/px），
且它与理论式 `(ADDSET + DATAST + 1) × 5 ns = 31 × 5 ns` **精确吻合** ——
即**每样本固定开销为 0**，预估里那“约 293 ns 的每笔访问固定开销”**并不存在**。

因此收紧 `ADDSET/DATAST` 的收益是**全额**的，而不是被固定开销吃掉大半：

| 档位 | 写脉宽 | 实测 ns/px | 整屏净耗时 | 全屏 FPS |
| --- | --- | --- | --- | --- |
| 15/15（原基线） | 75 ns | 154.97 | 23.81 ms | 42 |
| **5/5（选定）** | **25 ns** | **55.00** | **8.45 ms** | **118** |

⇒ 实测收益 **2.8×**，远超原先估计的 1.3–1.6×。**七档全部通过三步自检**（含 `4/4 = 20 ns`），
固化为 `5/5` 以保留 6 ns 裕量。**不需要**去碰 MPU。

### 2.2 约束

| 项       | 值                                                                                  |
| ------- | ---------------------------------------------------------------------------------- |
| 面板要求写脉宽 | `tWRL ≥ 19 ns`                                                                     |
| 当前值（基线） | `ADDSET 15 / DATAST 15` = **75 ns**                                                |
| 厂商例程值   | `3 / 3` = **15 ns** —— **低于 19 ns，实测整屏花屏，禁止使用**                                    |
| 扫描区间    | `12/12`、`10/10`、`8/8`、`6/6`、`5/5`（5/5 = 25 ns，留 6 ns 裕量）、`4/4`（20 ns，及格线边缘，仅作边界探测） |

`BWTR1` 编码：`ADDSET | (DATAST << 8)`，位于 `0x5200_4104`。

### 2.3 改哪里

`E:\stm32-tetris\src\lcd.rs`：

- `const BWTR1_VAL: u32 = 15 | (15 << 8);` —— 基线写时序
- `const BWTR_FAST_COMMON: u32` / `BWTR_FAST_7789: u32` —— `speed_up()` 用的值，当前也是 15/15
- 增加一个**仅用于扫描**的编译期开关（例如 `const BWTR_SCAN: Option<(u8,u8)>`），  
  让 6 个档位可以不改逻辑地分别构建、烧录、测量

⚠ `init_fmc()` 里 `FMCSEL` 保持复位默认（HCLK3），**不要**改 `BWTR` 以外的任何 FMC 寄存器。

### 2.4 测量与判据（**每个档位都要跑完整这三步**）

1. **整屏 ramp 自检**：调用现成的 `lcd::ramp_check_pub(&lcd, slot)`（整屏写“像素 i = i”再  
   回读比对），读 `LCD_DBG[slot]`，**失配数必须为 0**。
   > ⚠ 这个函数曾有一个**读指针错位 bug**：`0x2E` 后先读 8 拍 `head`（1 拍哑读 + 7 个真实
   > 像素）却仍从 `i = 0` 比对，导致**任何**时序下都恒报全失配（153600），看起来像“每档都花屏”。
   > 已于阶段 0 修复（读第二遍前重新发窗口命令 + `0x2E` 复位指针）。`dump_gram` 有同源问题
   > （图像漂移 7 像素），一并修掉。详见实测记录 §2。
2. **跑满 100 帧渲染后再测一次**：这是关键。本项目的历史经验是  
   *"初始化后紧跟的 ramp 自检 0 失配（纯长突发不受影响），但跑完 `render()`（成千上万次  
   小命令+数据）之后同一自检 15 万失配"*。**初始化后测一次通过不算通过。**
3. **抓屏目视复核**：把 `DUMP_MODE_CAPTURE` 打开，用 `E:\stm32-tetris\tools\grab_screen.py`  
   经 SWD 读出 AXI SRAM（`0x2400_0000`）里的截图，**必须亲眼看过**确认无花屏、无错位、  
   无横向压缩。只信失配计数不够。

## 3. 阶段 1：新建独立 C 工程

### 3.1 为什么不塞进 `stm32-tetris`

`stm32-tetris` 是 Rust `#![no_std]`、无 allocator；YMGUI 需要 `GY_malloc0/1`。  
混编会让工具链和内存模型分叉。**新建独立固件**，`stm32-tetris` 只作参照。

### 3.2 工程布局

```text

├─ CMakeLists.txt
├─ cmake\arm-none-eabi.cmake        # 交叉编译工具链文件
├─ linker\stm32h743vit6.ld
├─ src\

│   ├─ board_mpu.c                  # MPU（值必须照抄 §0.4 第 1 条）
│   ├─ board_clocks.c               # PWR VOS0 + PLL1 → sys_ck 400 MHz
│   ├─ lcd_fmc.c                    # FMC 寄存器 + flush_cb
│   ├─ lcd_init_st7796.c            # 厂商初始化序列
│   ├─ touch_gt9xxx.c               # 软件 I2C + GT9xxx
```

### 3.3 工具链

- **arm-none-eabi-gcc + CMake**。理由：YMGUI 是 C99 + **GNU 扩展**，Keil AC5/AC6 不友好。
- 先探测 `arm-none-eabi-gcc` 是否在 PATH；缺失则安装 ARM GNU Toolchain。
- 构建产物是 ELF，**probe-rs 可以直接烧录与调试**（与本项目现有调试链路一致）。

### 3.4 链接脚本（⚠ 写错直接 HardFault）

**绝不能从 `0x2000_0000` 一铺到底。** H7 的 RAM 分散且不连续：

```text
0x0000_0000  64 KB   ITCM
0x2000_0000 128 KB   DTCM          <- 栈、热代码、GY_malloc0 档
0x2002_0000 ~ 0x23FF_FFFF          <- 保留区，不可访问（铺过去就 HardFault）
0x2400_0000 512 KB   AXI SRAM      <- GY_malloc1 档（draw buffer、图片、堆）
0x3000_0000 128 KB   SRAM1 (D2)
0x3002_0000 128 KB   SRAM2 (D2)
0x3004_0000  32 KB   SRAM3 (D2)
0x3800_0000  64 KB   SRAM4 (D3)
```

至少声明 `DTCM` 与 `AXI SRAM` 两段。`0x9000_0000` 是 QSPI 映射区（只读，见 §6），  
**不进链接脚本的 RAM 段**。

### 3.5 最早必须做的两件事

1. **MPU 配置 FMC 区**（`0x6000_0000`，64 MB）为强序 —— 必须在任何 FMC 访问之前，  
   晚一步就花屏。配置值见 §0.4。
2. **使能 FPU**（CPACR 的 CP10/CP11）—— 应用层要用 float。  
   库的 Q15 数学**不动**。

## 4. 阶段 2：显示（`flush_cb`）

### 4.1 YMGUI 的契约（这是整个库对硬件的唯一要求）

```c
typedef struct GYdisp {
    GYcoord hor_res, ver_res;   // 320, 480
    GYpx*   buf1;               // draw buffer，可远小于整屏
    GYpx*   buf2;               // 必须 NULL（见 §0.4 红线 4）
    uint32  buf_px_cnt;         // 每块像素数
    void (*flush_cb)(struct GYdisp* d, const GYrect* area, const GYpx* buf);
    void*   user_data;
} GYdisp;
```

`flush_cb` 要做的就是把 `buf` 里 `area` 大小的连续像素推给面板：

```c
static void lcd_flush(GYdisp* d, const GYrect* a, const GYpx* buf) {
    (void)d;
    lcd_set_window(a->x1, a->y1, a->x2, a->y2);   // 写 0x2A/0x2B，再写 0x2C
    uint32 n = (uint32)(a->x2 - a->x1 + 1) * (a->y2 - a->y1 + 1);
    volatile uint16_t* ram = (volatile uint16_t*)0x60100000u;   // LCD_RAM
    for (uint32 i = 0; i < n; i++) ram[0] = buf[i];
}
```

**建议 draw buffer**：`320 × 40 px × 2 B = 25.6 KB`（`buf_px_cnt = 12800`）。  
库的 band 机制会自动按此切块，`flush` 次数多但正确性不受影响。

### 4.2 从厂商 C 源码取现成实现

### 4.3 四个必须做的修正（照抄厂商例程会坏）

1. **强制 `COLMOD = 0x55`**：跑完厂商 ST7796 序列后面板停在 `0x66`（18 bpp），  
   而 16 位 8080 总线上 18 bpp 要求每像素写两次 —— 只写一次会导致**整屏横向压缩一半**。  
   在初始化序列之后显式写 `0x3A = 0x0055`，并用 `0x0C` 回读确认。
2. **收回背光控制权**：厂商序列末尾写 `0x53 = 0x2C`（屏内控制背光）+ `0x55 = 0x82`（开 CABC），  
   而本板背光是**主机**用 PB1 控制的。冲突后果：画面偏暗时 CABC 把背光压到近黑、内容变化时闪烁。  
   必须强制 `0x53 = 0x0000`、`0x55 = 0x0000`。
3. **写时序不要照厂商"提速"**：厂商的 `3/3` 是按它自己的 220 MHz FMC 时钟算的  
   （3 周期 = 13.6 ns），在本机 200 MHz 下只有 15 ns，**低于面板要求的 19 ns**。  
   用阶段 0 实测出来的档位。
4. **竖屏**：`MADCTL = 0x08`（仅 BGR 位），按 320×480 排版。屏是物理竖装的，  
   按横屏初始化画面会整体旋转 90°。

**本节最值得记住的一个坑 —— 它和"输入"本身毫无关系：**

`YMGUI_Inject_Pointer()` 一被调用主循环就停住，表现为"死循环"。
**实际是 BusFault 升级成的 HardFault**（厂商模板的 fault handler 就是 `while(1)`，
与死循环外观完全一致）。根因是：

> **newlib 的 sbrk 堆起点（链接符号 `end`）与 YMGUI 的 `heap0` 起点是同一地址
> `0x2000_04B0`。**
> 厂商驱动里的 `printf`（`gt9xxx.c:132`、`lcd.c:684`）首次调用时，newlib 用 `malloc`
> 经 `sbrk` 给 stdout 分配行缓冲 —— 拿到的就是 YMGUI 的 heap0；
> 于是 `"CTP ID:1158\r\n"` 这 13 个字节被写进 `0x2000_04B8`，
> **正好盖掉 `ctx->root` / `ctx->top_layer`**。
> 再调注入，`hitRecD(obj=ctx->root=0x0D383531)` 读 `obj->state` → `BFAR=0x0D38353F`
> 精确总线错误 → HardFault。

定位于：读内核故障寄存器（`HFSR`/`CFSR`/`BFAR`）→ GDB 取栈上异常帧得 `pc` →
`objdump` 反汇编确认 `ldrb r3,[r3,#14]` 且 `0x0D383531+0x0E == BFAR` →
读 ctx 发现 `root`/`top_layer` 是垃圾而 `disp` 正常 → dump 堆区看到那段 ASCII。

修法（三层）：① 链接脚本独立划出 16 KB 的 `_sbrk_start.._sbrk_end`，
`_heap0_start` 后移，并自写 `_sbrk()`；② 删掉厂商驱动里 4 处 `printf`
（现在 ELF 里 `printf`/`malloc`/`__sf`/`_impure_ptr` 全部不存在）；
③ 新增 `src/board_fault.c` 故障快照，**以后故障不会再被误判成死循环**。

> ⚠ 给后续阶段的提醒：**§3.4 的链接脚本必须保证 sbrk 区与 heap0 不重合**；
> **不要在裸机路径上引入任何 `printf`/`malloc`**。这两条已经踩过一次。
> 另外注意本工程开了 `--gc-sections`：**只写不读的诊断全局会被删掉**
> （`g_boot_magic` 就中招过，`__attribute__((retain))` 在本机 ld 上无效），
> 新增诊断量时要么让 `main` 里写一次，要么用 `nm` 核实在 ELF 里确实存在。

## 6. 阶段 4：只读常量上 W25Q128

### 6.1 三个概念先说清

1. **不是"拿 8 MB 出来映射"**：进 memory-mapped 模式后 `FSIZE` 决定窗口，  
   W25Q128 设 **23** ⇒ **整颗 16 MB 全部映射到 `0x9000_0000` 起**。  
   要分的是**内容布局**，不是映射范围。
2. **XIP 区是只读地址空间，不是 RAM**：不能放栈/堆/变量。它替代的是内部 Flash（代码＋常量）。
3. **memory-mapped 与写 Flash 互斥**：写/擦前必须 `CR.ABORT` 退出映射，且退出时不能有  
   未完成访问；写完再重进映射。

### 6.2 QSPI 的三个必踩坑（照厂商 HAL 源码才发现，逐条都是）

1. **片选必须自己配**：HAL 的 `Qspi::bank1()` 的引脚列表里**只有 SCK 和 IO0~IO3，没有 NCS**。  
   漏掉 PB10 的 AF9 配置 ⇒ 片选悬空 ⇒ 读回永远 `0xFF`。
2. **数据寄存器按 8 位访问**（仅 indirect 模式涉及）：FIFO 按访问宽度弹数据，  
   32 位读一次弹走 4 字节只留 1 个 ⇒ 现象是"第一个字节对、后面全超时"。
3. **事务一次配完，顺序 `DLR → CCR → AR`**：拆成两步的后果是"不带地址的事务全通，  
   带 24 位地址的全不启动"（超时瞬间 `SR` 里 BUSY=0 且 TCF=0）。

### 6.3 进入 memory-mapped 模式

在 indirect 模式完成初始化（退出 QPI、置 QE 位、读 ID）之后：

```c
// CCR: FMODE = 0b11 (memory-mapped), 沿用 0xEB 快读 + 6 dummy cycles
qspi->dlr = 0;                       // 映射模式不需要长度
qspi->ccr = (0b11u << 26)            // FMODE
          | (0xEBu << 0)             // INSTRUCTION
          | (0b01u << 8)             // IMODE  1 线指令
          | (0b11u << 10)            // ADMODE 4 线地址
          | (0b10u << 12)            // ADSIZE 24 位
          | (6u    << 18)            // DCYC   6 个空周期
          | (0b11u << 24);           // DMODE  4 线数据
                                  // 位域以 RM0433 QUADSPI_CCR 为准，务必逐位核对
// AR: 映射模式不需要写地址
```


> ⚠ 上面的位域按 RM0433 的 `QUADSPI_CCR` 落位，**动手前必须逐个字段对照手册确认**，  
> 不要直接抄。`FSIZE` 必须是 23。

### 6.4 布局（16 MB）

| 偏移                         | 内容                                                        | 访问方式                              |
| -------------------------- | --------------------------------------------------------- | --------------------------------- |
| `0x9000_0000` + 0 ~ 1 MB   | 字模：完整 GB2312 16×16 4bpp（≈845 KB，第 i 字在 **i×128** 偏移，连续排布） | memory-mapped，`glyph_read = NULL` |
| + 1 ~ 3 MB                 | 图片/壁纸常量                                                   | memory-mapped                     |
| + 3 ~ 6 MB                 | IME 词典载荷（见阶段 5）                                           | memory-mapped，原地二分查找              |
| + 6 ~ 15.9 MB              | 文件系统区（LittleFS / FatFS 任选）                                | indirect，**写前退映射**                |
| **最后 1 个扇区 `0x00FF_F000`** | **留空**（`stm32-tetris` 的自检占用此处，若将来共用需避让）                   | —                                 |

### 6.5 字体接入（库侧零改动）

YMGUI 的 `GYfont.glyph_read` 有两条官方路线：

- **`glyph_read = NULL`** ⇒ 直接用 `bitmap` 指针（**内部 flash 或映射 flash 都支持**）
- 置回调 ⇒ 先拷字节进 RAM 再 blit（用于非映射的 SPI flash）

本方案走第一条：`GYfont.bitmap = (const uint8_t*)0x90000000u;`，`glyph_read = NULL`。

⚠ 这省掉的是"每个字模 128 B 拷进 RAM 再 blit"这一趟；  
**RAM 常驻收益 ≈ 0**（YMGUI 本来就是逐字取模）。真正省下的是**内部 Flash** 与  
"可以用完整 GB2312 而不必精简字集"。

### 6.6 验收（确定性判据）

对同一偏移 `off`，比较两种读法的结果：

- memory-mapped：读 `*(volatile uint16_t*)(0x9000_0000u + off)`
- indirect：走自己的 `qspi_read()`（0xEB 单次读）

**逐字节比对，必须完全一致。** 擦写后退出映射、重进映射，再比一次。

顺带提醒：**不要用 SWD 直接读 `0x9000_0000` 当验收手段**，可能极慢或失败。

**踩到的三个坑（§6.2 那三条已预先规避，这三条是新踩的）**

1. **模式码里数据模式位写错** —— `mode[7:6]` 是数据模式，`0` = **无数据阶段**。
   把"单线读状态/读 JEDEC ID"写成 `(0u << 6)`，函数却按间接读配了 `FMODE=01`+`DLR=0`，
   控制器于是等一个**永远采不到的数据阶段**：`SR.BUSY` 恒 1、`SR.FLEVEL` 恒 0，全部读超时。
   **症状与"片选悬空/芯片没焊"完全一样**。
   区分手法：**无数据阶段**的命令（`0x06` 写使能 / `0xFF` 退 QPI）若成功，就说明
   控制器、时钟、引脚都正常，问题在数据阶段；再读回 `CCR`+`DLR` 就能看到
   "要收 1 字节但 DMODE=0"这个自相矛盾。
2. **§1.2 的引脚顺序要更正**（见上文 §1.2 的更正块）：实测 `IO2=PE2、IO3=PD13`。
3. **XIP 区必须显式加 MPU 区域**：`HAL_MPU_Enable(MPU_PRIVILEGED_DEFAULT)` ⇒ `PRIVDEFENA=1`，
   未映射地址落 ARM 默认存储图（`0x8000_0000~0x9FFF_FFFF` 是"可缓存 Normal"）。
   本工程取 `PRIV_RO` + 非缓存 + 非缓冲 + XN=1：
   只读（误写立即 MemManage）、每次读真走 QSPI（与 indirect 可比、无需 cache 维护）、
   不从 XIP 取指。**若将来改成可缓存以提升字模读性能，必须同时补
   `SCB_CleanInvalidateDCache()`。**

**字模/常量数据的灌入不在本阶段**：本阶段是机制 + 验收；按 §7.2 的降配表，

"退出映射 → 读-改-擦-写回"）。

| `g_synth_done` | 0 → 2 | 合成滑动 + 合成单击都跑完按下/移动/抬起全程 |
| 堆水位 | heap0 峰值 31.1/57.8 KB（54%）；**heap1 峰值 205.2/212.0 KB（97%）** | heap1 余量只剩 ~7 KB，见 §9 第 6 条 |

## 7.6 性能优化：从 48.8 FPS 到 130.2 FPS（2026-10-03 收尾优化）

阶段 6 交验收时 A1 记的是 **48.8 FPS**（整屏 flush 20.50 ms）。收尾时顺着这条线往下挖，
发现那 20.50 ms **绝大部分不是总线付的**，而是编译与写法上的代价。四项改动后同一个钩子
读到 **7.68 ms ⇒ 130.2 FPS**，正好压在 §2 算出的总线地板上。

### 7.6.1 根因：整个工程此前是 `-O0` 编译的

这是本次最有价值的发现。`CMakeLists.txt` 从来没有设置过 `CMAKE_BUILD_TYPE`，工具链文件里
也只写了 MCU 相关 flags、**没有任何 `-O`** ⇒ gcc 按默认的 `-O0` 编译了全部 300+ 个源文件。

反证线索其实一直在代码里：`third_party/BSP/LCD/lcd.c` 的 `lcd_wr_data()` 有一句
`data = data;   /* 使用-O2优化的时候,必须插入的延时 */` —— 厂商的验证基线是 `-O2`，
而本工程移植时把厂商代码搬过来、却没把优化等级一起搬过来。

### 7.6.2 四项改动（严格分步做的，每步单独上板量过）

| 步骤 | 改动 | 整屏 flush | FPS | 相对基线 |
| --- | --- | --- | --- | --- |
| 基线 | `-O0` + `lcd_wr_data()` 逐像素调用 | 20.50 ms | 48.8 | — |
| ① | `CMakeLists.txt` 加 `-O2` | 13.97 ms | 71.6 | **1.47×** |
| ② | flush 热点改内联 volatile 写（绕过跨 TU 调用） | **7.68 ms** | **130.2** | **2.67×** |
| ③ | 主循环固定 `delay_ms(15)×2` → 按实际用量补足 16 ms | 节拍 33.3 → **66.2 Hz** | — | 2.0× |
| ④ | XIP 区改可缓存（**证伪，已回退**） | 64.80 → 64.69 ms（无效） | — | 无收益 |

关于 ②：每像素 irreducible 的开销是调用 `lcd_wr_data()` 的 call/return 与那句人为延时。
`-O2` **不会跨越编译单元内联**，所以②必须在 `ymgui_port.c` 里自己写：

```c
#define LCD_RAM_PX ((volatile uint16_t *)0x60100000u)
static inline void lcd_wr_px_inline(uint16_t v) { *LCD_RAM_PX = v; }
```

去掉厂商那句 `data = data;` 是**安全的**：总线侧的写脉宽 25 ns 由 **FMC 按 DATAST 寄存器自己拉**，
与 CPU 快慢无关；CPU 写太快时 FMC 用 HREADY 反向压住 AHB，不会丢数据。判据仍然是
`g_ramp_mismatch` / `g_gram_mismatch` —— 本次改完复跑，两者均为 **0**。

### 7.6.3 关于 ③：主循环节拍

原来是一拍 30 ms（`delay_ms(15)` ×2），那是在 flush 还要 20.5 ms 的年代定的。
flush 降到 7.7 ms 之后，30 ms 的固定节拍反而成了上限 **33.3 FPS** —— 再快的 flush 也白搭。
改成"本轮花了多久就补多少、凑够 16 ms"之后节拍恒定在 **66.2 Hz**，
触摸轮询与 UI 响应率跟着翻倍。动画速度不受影响，因为 `Inject_Tick(ms)` 本来就用 DWT 实测毫秒。

顺带把 LED 心跳改成固定 2 Hz 且与帧频解耦 —— 挂在帧循环里翻转的话，帧率一变 LED 闪烁频率
就跟着变，很容易被误读成"主循环卡了"。

### 7.6.4 ⚠ 关键结论：**flush 已经不是瓶颈，渲染才是**

新加了 `g_bench_frames`（写 N 启动，每帧强制 `YMGUI_Ctx_InvalidateArea` 整屏脏）做端到端基准：

| 场景 | 每帧耗时 | FPS |
| --- | --- | --- |
| 裸写整屏（`g_flush_cyc`） | 7.68 ms | 130.2 |
| 真实 `flush_cb` 全成本折算（含窗口命令 + 镜像 memcpy） | ≈ 8.76 ms | ≈ 114 |
| **满负载最坏情况（强制整屏每帧重绘）** | **64.80 ms** | **15.4** |

⇒ 最坏情况下 **渲染占 54.88 ms（85%），flush 只占 9.92 ms（15%）**。

所以"再优化 flush 也涨不了多少帧率" —— 这一步已经见底（130.2 FPS 就是 §2 的总线地板）。

### 7.6.5 已试过但被证伪的一条（不要重复投入）

**假设**：每画一个中文字都要真的走一遍 QSPI 取字模，是渲染慢的主因。
**做法**：XIP 区（`0x9000_0000`）改为 `CACHEABLE|BUFFERABLE`，并在 `qspi_enter_mmap()`
开头加 `SCB_CleanInvalidateDCache()`，形成"每次进映射都清一次"的闭环。
**结果**：满负载帧基准 **64.80 → 64.69 ms**，纹丝不动（15.4 → 15.5 FPS，纯噪声）。
**结论**：字模读取**不在**渲染的开销构成里。改动只带来 cache 维护负担、不带收益 ⇒ **已回退**，
并在 `mpu.c` 里留下记录。真正的开销是**纯 CPU 软件光栅化**（圆角、渐变、alpha 混合、位图缩放）。

另一个堵死的方向：`DRAW_BAND_ROWS` 从 32 增大可减少每帧 traversing 对象树的次数，
但 draw buffer 随之增长，而 **heap1 峰值已达 205.2/212.0 KB（97%）**，腾不出空间。

### 7.6.6 优化后的全套验收

| 判据 | 结果 |
| --- | --- |
| A1 裸写整屏 | **130.2 FPS**（7.68 ms），总线地板 50.0 ns/px 已到底 |
| A2 双一致性 | `g_ramp_mismatch = 0`、`g_gram_mismatch = 0` |
| A3 触摸 ID | `g_tp_pid` 不变 |
| 主循环节拍 | 66.2 Hz（原 33.3 Hz） |
| 故障快照 | `g_fault[0..8]` 全 0 |

| 代码尺寸 | text 1,613,100 → 1,555,100 B（**-3.6%**，`-O2` 顺带的收益） |

### 7.7 上电第一屏的"彩色波纹"与开机自检开关（2026-10-03 追加）

**现象**：上电瞬间屏幕会闪一下花花绿绿的彩色波纹（横向 32 px 一条蓝循环、
每 6.4 行跳一次红分量，叠加成斜向摩尔纹），约 **86 ms** 后自动恢复成开机画面。

**它不是花屏、不是时序故障，是 A2 的 ramp 自检图案**：
`ymgui_port_ramp_selftest()`（`src/ymgui_port.c`）把整屏 GRAM 写成
「像素 i = i & 0xFFFF」，再整屏读回比对，证明 **8080 读通路本身可信**——
没有这一步，`g_gram_mismatch` 的失配数分不清是"没写进面板"还是"读坏了"。
写 7.68 ms + 读 71 ms（读时序 ADDSET=15/DATAST=78 @200 MHz ≈ 465 ns/px）
+ 恢复写 7.68 ms ≈ 86 ms，写的过程中面板边扫边被改写，所以看起来是"闪"。

**开关（2026-10-03 起默认关闭）**：

| 层 | 位置 | 说明 |
| --- | --- | --- |
| 编译期宏 | `src/ymgui_port.h` 的 `YMGUI_PORT_BOOT_SELFTEST`（默认 **0**） | =1 时上电自动跑 ramp + gram_verify |
| CMake 注释位 | `CMakeLists.txt`（`YMGUI_DIAG_OBJTIME` 之后） | 取消注释 `add_compile_definitions(YMGUI_PORT_BOOT_SELFTEST=1)` 即可打开 |
| **运行时钩子（推荐）** | 主循环 `g_gram_recheck`，SWD 写 1 触发 | 随时重跑同一套自检，**不用重编译**；AI/脚本走这条通道 |

默认关的唯一目的：正常上电看不到这一闪。关闭**不损失**自检能力——
A2 复测照旧用 `g_gram_recheck`。上电后如果两个变量保持初值 `0xFFFFFFFF`
（而不是 0），即说明本固件编译时自检是关的，属预期。

`YMGUI_Refresh(s_ctx)`（开机动画第一帧）**不受宏控制、仍然无条件执行**，
所以关掉自检不会引入白屏停留。

**验证记录（上板实测）**：
- 宏=0 烧录 → 复位 → `g_ramp_mismatch`/`g_gram_mismatch` 保持 `0xFFFFFFFF`（没跑）；
  写 `g_gram_recheck=1` 后两者均变 0（钩子通道完好）。
- 宏=1 烧录 → 复位 → 两个 mismatch 直接为 0（上电自检真的跑了）。
- 改回宏=0 重新烧录 → 抓屏（`build/boot_selftest_off.png`）桌面正常。

## 10. 执行纪律（给执行者）

1. **先量测，再改**。阶段 0 不做完、不拿到那张实测表，不要开始阶段 1。

3. **报告"通过"之前先证伪自己**：换一次运行条件再测一遍（例如跑满 100 帧后再 ramp）。
4. **失败就记明并停**，不要自行放宽红线（尤其 §0.4 第 1 条）。
5. **所有硬件等待带超时上限**；厂商代码里全是死等，照抄会让链路不通时整块板卡住。
6. **每处反直觉的取值都写注释说明根因**，否则后来的人一定会改回去。
