## 1. 测量方法与口径（先说清楚数字怎么来的）

凭感觉调参数会得出错误结论，所以这次先把三个可分离的测量手段建起来：

### 1.1 band 行数扫描 → 分离"固定开销"与"填充开销"

一帧满负载的时间可以拆成

```
T = n_bands × A  +  P × b
```

- `A` = 每 band 的**固定开销**：从 root 递归整棵对象树、每个对象算绝对区域、做相交测试。
  与 band 内有多少像素**无关**。
- `P` = 本帧实际填充的像素数（整屏标脏时恒为 153600），与 band 数无关。
- `b` = 每像素**填充开销**：光栅化、alpha 混合、缩放采样。

每个 band 都要从 root 重画一遍 ⇒ `n_bands` 越大，`A` 付得越多而 `P` 不变。
量两个不同 `n_bands` 就是二元一次方程组，直接解出 `A` 和 `b`。

`disp->buf_px_cnt` 是**运行时字段**（库每帧现读来算 band 高度），不是 init 时算死的，
所以加一个 SWD 可写的 `g_band_rows` 就能扫描，**不用重新编译**。
工具：`tools/render_scan.py`。

### 1.2 图元微基准 → 每种绘制的每像素单价

直接构造一个指向真实 draw buffer 的 `GYsurface`，单独调一次图元，DWT 计时。
钩子：`g_micro_test`（1=不透明填充 / 2=半透明填充 / 3=缩放 blit / 4=中文文字 / 5=圆弧 ×100）。

### 1.3 图元像素计数 → overdraw 与碎调用程度

`YMGUI_DIAG_FILLPX` 打开后，库会计数：
- `g_diag_fill_px/calls/opa_px`：`Draw_Fill` 填了多少像素、调了几次、其中多少走 alpha 混合
- `g_diag_putpx/blendpx`：`GY_PutPx` / `GY_BlendPx` 的实际写入次数
  （**文字、圆弧、线条最终都走这两个出口**，所以能覆盖所有非 `Draw_Fill` 的逐像素写入）

## 2. 渲染耗时分布（实测）

优化前的满负载一帧 **62.22 ms**：

| 项 | 耗时 | 占比 | 依据 |
| --- | --- | --- | --- |
| 壁纸逐像素 `GY_PutPx` | **20.77 ms** | 33% | 优化前后**差值实测** 62.22 → 41.45 |
| `Draw_Fill` | ≈17.03 ms | 27% | 347938 px，按微基准单价估算（见 §2.1  caveat） |
| flush（推给面板） | 9.92 ms | 16% | `g_flush_cb_cyc` 实测折算 15 bands |
| 每 band 固定开销 A×15 | 4.02 ms | 6% | band 扫描解出 `A = 0.268 ms/band` |
| 其余（文字 / 圆弧 / 其他绘制） | ≈10.5 ms | 17% | 余项，**尚未细分** |

### 2.1 一个必须说明的不确定性

`Draw_Fill` 的 17.03 ms 是"像素数 × 微基准单价"**估**出来的，可能**偏低**：
微基准测的是 320×32 的**连续大块**，而真实调用是 **5474 次、平均每次只有 63.6 px**
的碎调用（碎调用的循环启动与裁剪计算摊到少量像素上，单价更高）。
所以 `Draw_Fill` 的实际占比可能高于 27%，"其余"相应更少。
**要精确拆分，需要给 `drawObjRec` 加 per-object 计时** —— 见 §5 的 P0-0。

## 4. 已实施并实测的优化

| # | 改动 | 位置 | 实测收益 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | **壁纸逐像素 → 行内指针直写** | `phone_shell.c` `wallpaper()`（应用层） | **62.22 → 41.45 ms（1.50×），省 20.77 ms** | ✅ 保留 |
| 2 | 圆弧开方前先平方预筛 | `YMGUI_DrawArc.c`（库） | 单次 **2.01×**，但整帧 **1.00×**（非热点） | ✅ 保留（无害） |
| 3 | `GY_MixPx` 三次 `/255u` → 乘加移位 | `YMGUI_DrawPx.h`（库） | 64.80 → 61.08 ms（**5.7%**） | ✅ 保留 |
| 4 | 圆角矩形中间实心带合并成一次填充 | `phone_ui.c`（应用层） | **≈0%** | ✅ 保留（无害，但无收益） |

### 4.1 改动 1 的细节（本次最大收益项）

原实现对壁纸**每个像素**做：`GY_PutPx()`（6 次边界比较 + 2 次减法 + 1 次乘法算索引）
**再加一次 `GY_ColorToPx()`**（打包 RGB565）。而抖动值每行只有 **4 种**，却每像素重算一遍。
壁纸是**全屏**背景 ⇒ 每帧 153600 px 全走这条路径。

改法：每行先算好 4 个抖动色放进 `dith[]`，裁剪在循环外一次性算好 `[x0, x1)` 与行首指针，
行内只做"查表 + store"。**写入的像素集合与颜色与原实现逐位相同。**
（裁剪安全性依据：`vis ⊆ clip ⊆ buf_area` 是库保证的不变量，`drawObjRec` 里 clip 只会被收窄。）

### 4.2 改动 3 的等价性证明

`(x + 1) * 257 >> 16` 在 **x ∈ [0, 65025] 上精确等于 `x / 255`**
—— 已用脚本对全部 65026 个取值逐一枚举验证，**零反例**。
而 `GY_MixPx` 里 `x = 分量 × opa + 分量 × inv ≤ 255 × 255 = 65025`，正好落在验证区间内，
所以是**逐位等价**，不引入任何色偏。

> ⚠️ 这条改动只拿到 5.7%，说明 **gcc 对常量除数 255 早已自动做了强度削减**，
> 手工再优化是重复的。这条经验值得记住：**先看编译器有没有替你做**。

### 6.1 P0 实施结果（2026-10-03 追记，全部上板实测）

三项 P0 全部落地。满负载整帧（60 帧折算，整屏标脏，15 bands）：

| 配置 | 每帧 | FPS | 相对上一行 |
| --- | --- | --- | --- |
| 基线（P0 之前） | 41.45 ms | 24.1 | — |
| + **P0-1** ribbon 合并（镜像开 + 计时开） | 37.64 ms | 26.6 | **省 3.82 ms** |
| + **P0-2** 全帧镜像关 | 35.13 ms | 28.5 | **省 2.51 ms**（预估只有 1–2 ms） |
| + 计时关（产线形态） | **34.84 ms** | **28.7** | 计时自身开销 0.28 ms（0.75%） |

累计 **1.19×**；相对本报告起点 62.22 ms 累计 **1.79×**。

#### P0-1 · ribbon 按行区间合并（`phone_shell.c`，应用层）

原实现对三层 ribbon **逐列**调 `Draw_Fill`（1 px 宽），一帧 **4558 次**非空调用；
改为"crest 相同的相邻列合并成一段 + 整段与本 band 行区间不相交就跳过"后降到
**1366 次**（省 70%）。像素总数不变（`g_diag_fill_px` 前后都是 347938）。

**等价性证明不是抓屏目视，而是软件 A/B**（`tools/check_ribbon_equiv.py`）：
在主机上把两种算法各跑一遍完整一帧（按 `Draw_Fill` 的真实裁剪语义、15 个 band、
半开区间求交），对每个像素记录 (层, 颜色, opa) 的**写入顺序序列**再逐像素比对——
**70415 个覆盖像素全部一致**。alpha 混合逐像素独立、每个像素每层只被写一次，
序列相同 ⇒ 结果逐位相同。脚本算出的 4558/1366 也与板上 `g_diag_fill_calls`
的差值（5474→2282，差 3192）严格吻合。

3.82 ms 的来源：省掉的 3192 次调用 + 约 85k 次"逐行重算行首指针"
（1 px 宽的填充每行只摊到 1 个像素）。两项无法用本实验分离，合起来就是
"碎调用的单价"——**结论：`Draw_Fill` 对窄矩形极不划算，能合并就合并**。

#### P0-2 · 全帧镜像开关（`ymgui_port.c`）

镜像缓冲（320×480×2 = 300 KB/帧）只服务两个诊断：A2 的 `gram_verify` 与
`grab_ymgui.py` 抓屏。改为两级开关：

- 运行时 `g_frame_mirror`（默认 **1**）：不重编译就能量收益；**跑 A2 前必须写回 1**
  并让它刷一整帧，否则 `g_gram_mismatch` 必然失配（面板与镜像各自演化）。
- 编译期 `YMGUI_PORT_FRAME_MIRROR=0`：量产形态，连拷贝都不编。

实测关掉省 **2.51 ms**（300 KB 拷贝 ≈ 8.3 cycles/byte 摊到 153600 px 上），
比 §6 预估的 1–2 ms 大。

#### P0-0 · per-object 计时（库内 `YMGUI_Invalidate.c`，`YMGUI_DIAG_OBJTIME`）

`drawObjRec` 拆成"计时外壳 + 递归本体"，每个被访问的对象记三项：
`self`（draw_cb 自身，不含后代）/ `sub`（含后代整棵子树）/ `calls`，
外加对象地址、draw_cb 地址、绝对区域。运行时总开关 `g_objtime_on`
（关掉只剩一次分支判断），`YMGUI_Diag_ObjTimeReset()` 清零——
`g_bench_frames` 启动时自动清，保证读到的就是"刚才那 N 帧"的分布。
读取与符号解析：`tools/objtime_scan.py`（nm 把 draw_cb 地址解析成函数名，
Thumb 指针的 bit0 已掩掉）。

**排行（60 个对象，60 帧折算，帧宽 37.64 ms）**：

| 对象（draw_cb） | 绝对区域 | self ms/帧 | sub ms/帧 | calls/帧 | self µs/次 |
| --- | --- | --- | --- | --- | --- |
| `wallpaper` | 0,0 320×480 | **15.231** | 22.711 | 15 | 1015 |
| `baseDrawCb`（root 背景） | 0,0 320×480 | **4.250** | 26.973 | 15 | 283 |
| `PhoneUI_glass_draw`（天气面板） | 22,151 276×79 | 1.796 | 2.501 | 4 | 449 |
| `PhoneUI_glass_draw`（dock） | 15,368 290×68 | 1.625 | 2.245 | 3 | 542 |
| `text_draw`（时钟区） | 22,37 240×66 | 0.961 | 0.967 | 3 | 320 |
| 其余 55 个对象合计 | — | ≈3.0 | — | — | — |
| **self 合计** | | **26.88** | | | |

结合图元单价（本轮复测：不透明填充 **11.07 cy/px**、半透明 **32.36 cy/px**）拆 `wallpaper`：

- ribbon 半透明填充：129893 px × 32.36 = **10.51 ms**（占 wallpaper 的 69%）
- 渐变行内直写：153600 px × ≈12.3 = **4.72 ms**（31%）
  —— 注意：**纯指针直写的地板也就是 11–12 cy/px**，与 `Draw_Fill` 不透明内层同档，
  说明这是"AXI SRAM 逐像素 store"的本征成本，算法层已无可挖，要快只能
  32-bit 双像素写或 P2-1 DMA2D。

⇒ **§2.1 里那笔"其余 10.5 ms 尚未细分"的账就此结清**：它不是某个神秘对象，
而是 `wallpaper`（15.23）+ `baseDrawCb`（4.25）+ 两块毛玻璃（3.42）+ 文字（≈2.4）的合计。

**下一刀的优先级据此更新**：P1-1（`Draw_Fill` 内层，直接打 ribbon 的 32.36 cy/px

#### ⚠ 更正（P1 轮证伪本节的一个结论）

本节曾写："纯指针直写的地板也就是 11–12 cy/px，与 `Draw_Fill` 不透明内层同档，
