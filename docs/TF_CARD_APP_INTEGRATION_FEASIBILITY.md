# TF 卡接入「文件管理器 / 相册」可行性报告

> **调研日期**：2026-10-08（L2-1~L2-4 + L3 全部完成、FatFs 上板验证通过之后）  
> **调研对象**：`apps/files.c` 的四个卡片（照片 / 录音 / 笔记 / 下载）+ `apps/gallery.c`

>
> **2026-10-08 修订**：初版只考虑软件解码，**漏了 H743 自带的硬件 JPEG 编解码器与 DMA2D**。

### 2.2 当前 App 的真实实现（决定了改造量）

- **`files.c`**：**零 IO**。四个卡片名是硬编码字符串数组 `folder_names[]`；  
  点进每个卡片后显示的 4 条也是硬编码二维数组 `entries[4][4]`  
  （例如录音卡片显示的是"未接入麦克风"、笔记卡片显示"未写入磁盘"）。  
  整个 App 只有 **4 个 `PhoneUI_button` 当列表行**（`file_rows[4]`），**没有滚动列表控件**。
- **`gallery.c`**：**没有图像**。3 个纯色块轮换（`RGB(196,105,113)` / `RGB(83,155,173)` / `RGB(149,128,204)`）
  - 名字数组 `{"01 / 珊瑚", "02 / 海岸", "03 / 暮色"}`，切换时改背景色。
- **`notes.c`**：有 `YMGUI_EditView`（容量 4096）+ 标题 `TextInput`（127），  
  底下一行写着"点击编辑 / 本次运行保留" ⇒ **内容只活在内存里，退出即丢**。  
  已有 `app_command("set-body", ...)` 挂 SWD 注入。
- **`recorder.c`**：纯状态机（`app_tick` 累加 `record_ms` + 动画条），  
  按钮文案是"开始**演示**录音"，`app_close` 写的是"演示已停止 · **未采集声音**"。

### 2.3 图像显示通路

`YMGUI_Image` / `YMGUI_Draw_Img` 存在且可用，但有一个必须知道的前提：

```c
typedef struct {
    const GYpx* data;     // 像素数据(行优先, stride = w) —— GYpx = RGB565, 16 bit
    GYcoord     w, h;
    uint8       use_key; GYpx key;
} GYimg;
```

> ⚠ **YMGUI 只负责 blit 和缩放，完全不做解码。**  
> 它要的是**已经解码成 RGB565 的连续像素数组**，整幅都在内存里。  
> 所以"接 TF 卡到相册"的真实工作量 = **把"卡上文件 → RGB565 数组"这一步补上**，  
> 而不是调一个 `YMGUI_Image_SetSrc("/photo.jpg")` 就完事。

### 2.4 ★ H743 自带的两个图像硬件外设（2026-10-08 补查，修正了初版结论）

初版报告只考虑了软件解码，**漏了本芯片自带的硬件**。查 `stm32h743xx.h`（ST 按型号生成的官方头文件）实证：

| 外设                   | 证据                                               | 能力                                                        | 对相册的价值                  |
| -------------------- | ------------------------------------------------ | --------------------------------------------------------- | ----------------------- |
| **JPEG 编解码器**        | `JPEG_TypeDef` / `JPGDEC_BASE` / `JPEG_IRQn=121` | **硬件 JPEG 解码**（Huffman + IDCT 全由硬件做）                      | ★ **不需要软件 tjpgd**       |
| **DMA2D（Chrom-ART）** | `DMA2D_TypeDef` / `DMA2D_BASE` / `DMA2D_IRQn=90` | 像素格式转换（`DMA2D_INPUT_YCBCR` → `DMA2D_OUTPUT_RGB565`）、混合、填充 | ★ **YCbCr→RGB565 硬件完成** |

`HAL_JPEG_MODULE_ENABLED` 与 `HAL_DMA2D_MODULE_ENABLED` 在 `stm32h7xx_hal_conf.h` 里**已经是开的**，  
`stm32h7xx_hal_jpeg.c/.h`、`stm32h7xx_hal_dma2d.c/.h` 也在 `third_party/STM32H7xx_HAL_Driver/` 里，  
**只是都还没编进 `CMakeLists.txt`**（当前 `grep hal_jpeg / hal_dma2d / hal_mdma` 均为空）⇒ 要用就加进去。

完整硬件链路（省 CPU，但**不省内存**，见下）：

```
TF 卡 ──SDMMC/IDMA──▶ JPEG 压缩数据缓冲
                        │  HAL_JPEG_Decode_DMA（输入/输出都走 MDMA）
                        ▼
                     YCbCr 输出缓冲（硬件解码结果，按 MCU 块吐出）
                        │  DMA2D M2M_PFC 模式
                        ▼
                     RGB565 缓冲 ──▶ YMGUI_Image 显示
```

#### ⚠ 但"硬解码 ≠ 不占内存"，三件事硬件做不到

1. **输出缓冲照样要**。硬件解码器替代的是 **CPU 的计算**（Huffman 解码、IDCT、色度上采样），  
   不是"把像素变没"。解出来的每一个像素都要落在内存里，否则 YMGUI 拿不到 `GYimg.data`。  
   ⇒ §3.1 那笔账（284×230 RGB565 = 130 640 B > 115 KB 余量）**依然成立**。
2. **没有硬件缩放**。`JPEG_CONFR0~CONFR7` 的全部位定义里**没有 SCALE 字段**  
   （只有 `CONFR3_XSIZE` / `CONFR1_YSIZE` = 源图尺寸）⇒ 硬解只能出原尺寸。  
   **DMA2D 也不能缩放**（`M2M_PFC` 只有格式转换，无缩放）⇒ 降采样仍只能由 CPU 做。
3. **输入数据要先到内存**。卡不能直接喂给 JPEG 外设，要先 `f_read` 到缓冲  
   （一张 284×230 的 JPEG 约 8~20 KB，可接受）。

> **净收益**：省掉 tjpgd 的 12~~15 KB FLASH 与 3~~6 KB 工作 RAM、省掉 CPU 的 Huffman/IDCT 时间  
> （这部分变成 MDMA 搬运 + 硬件流水线）、YCbCr→RGB565 由 DMA2D 硬件完成。  
> **净代价**：要把 `hal_jpeg.c` / `hal_dma2d.c` / `hal_mdma.c` 编进来，且三个外设都要配置时钟与中断。

## 3. 五条硬约束（所有方案都要过这五关）

### 3.1 内存：相册**放不下一张全尺寸图** ★最关键

| 项                                    | 数值                                      |
| ------------------------------------ | --------------------------------------- |
| 屏幕                                   | 320 × 480，RGB565（2 B/px）                |
| 相册面板尺寸（`gallery.c`）                  | 284 × 230                               |
| **全尺寸 RGB565 解码结果**                  | 284 × 230 × 2 = **130 640 B（127.6 KB）** |
| heap1 总容量（`0x2404B000`~`0x2407E000`） | **204 KB**                              |
| heap1 峰值（实测，含开机以来累计）                 | **89 000 B**                            |
| **heap1 可用余量**                       | **≈ 115 KB**                            |

> **127.6 KB > 115 KB ⇒ 全尺寸图解出来就放不下**，而且是"放不下"不是"紧张"。

**出路：解码时降采样**（只往目标缓冲写抽样到的像素，不生成全尺寸中间结果）：

| 采样率     | 输出尺寸        | 缓冲           | 是否放得下 |
| ------- | ----------- | ------------ | ----- |
| 1/1     | 284×230     | 130 640 B    | ❌ 放不下 |
| **1/2** | **142×115** | **32 660 B** | ✅ 宽松  |
| 1/4     | 71×57       | 8 094 B      | ✅ 很宽松 |

显示时用 `YMGUI_Draw_ImgScaled()`（已有，定点最近邻）把 142×115 放大回 284×230，  
配 `GY_IMG_FIT` 模式。代价是 2× 放大后偏软 —— **这是内存约束下的必然取舍，不是设计缺陷**。

### 3.2 FLASH 余量：够，但不能乱加库

```
已用 1 779 380 B / 2 097 152 B = 84.85%
余量            317 772 B ≈ 310 KB
```

够放：BMP 解码（~2 KB）、目录浏览（~6 KB）、笔记落盘（~~3 KB）。  
**够但不宽裕** —— 若要上 JPEG 解码库（tjpgd 全功能约 12~~15 KB）仍在预算内，  
但**不建议同时上 PNG**（inflate 约 +40 KB）。

> 若将来吃紧，已知最大单项是 `ffunicode.c` 的 GBK 双表 `uni2oem936`+`oem2uni936`  
> 各 87 172 B、合计 **174 344 B**；`FF_CODE_PAGE` 936→437 可省 ~170 KB，  
> 代价是**中文文件名变乱码**（文件内容不受影响）。

### 3.3 帧预算：卡 IO 和解码都是阻塞的

| 项                | 数值                                       |
| ---------------- | ---------------------------------------- |
| 主循环帧预算           | `FRAME_TARGET_MS = 16`（`src/main.c:731`） |
| 当前满负载实测          | **10.89 ms**（`README.md` A1）             |
| FatFs 轮询读 4096 B | 0.90~1.15 ms                             |
| FatFs 写 4096 B   | 1.5~4.8 ms（波动大，卡内编程主导）                   |

**FatFs 是同步阻塞 API，没有异步版本。** 单帧内最多能安全吃掉约 **5 ms**（16 − 10.89）。  
所以：

- 一次 `f_readdir` 枚举**必须限量**（建议 ≤ 32 条/次），大目录要**分帧推进**；
- JPEG 解码一张 320×240 估计 30~80 ms，**远超预算** ⇒ 必须分帧/状态机解码，不能一把梭。

### 3.4 UI 结构：没有滚动列表

`phone_ui.h` 提供的控件只有：`label` / `button` / `panel` / `app_text` / `app_input` / `bar` / `switch` / `slider`。  
**没有 list / scroll 控件**。`files.c` 现在就是拿 4 个 button 充当列表行。

⇒ 真实目录（几十个文件）只有两条路：

1. **分页**：保留 4 行，加"上一页 / 下一页" —— 改动最小，与现有 `app_back()` 语义一致；
2. 复用 `files_manager.c`（`project_Demo/files_manager/`，960×600 树形浏览）—— 但那是 **960×600 布局**，  
   本屏是 320×480，**不能直接搬**，要重排。

**建议走 1（分页）**，改动最小且能立刻给出整数判据。

### 3.5 硬件：板上没有音频器件 ★录音卡片的死结

查厂商原理图 `STM32H743VIT6 V1.2_SCH.pdf`，全文检索 `MIC / 麦 / SPK / 喇叭 / AUDIO / I2S / SAI / WM89 / VS10 / 耳机 / DAC`：  
**唯一命中的是 "Micro SD Card"，没有任何音频器件。**

`stm32h7xx_hal_conf.h` 里 `HAL_I2S_MODULE_ENABLED` / `HAL_SAI_MODULE_ENABLED` 虽然是开的，  
但那是**从厂商模板继承的模块开关**，工程内**没有任何 I2S/SAI 驱动代码**，板上也没有对应外设。

⇒ 录音卡片**既不能录也不能放**。唯一能做的是"列出卡上音频文件名 + 大小"，  
即**降级成只读文件清单**，且要在 UI 上明确写清"本板无音频器件"，不能假装能播。

## 4. 四个卡片逐一分析

### 4.1 笔记 —— ✅ 完全可行，建议第一个做

**现状**：`notes.c` 有 `YMGUI_EditView`（4096 容量）+ 标题输入（127），  
`app_command("set-body")` 已挂 SWD。**内容退出即丢**。

**改造**：加"保存到卡 / 从卡加载"两个按钮，读写 `/YMGUI/notes/*.txt`。  
`/YMGUI` 目录在 `fs_check` 自检里**已经建好了**（`FS_TEST_DIR`），直接复用。

**为什么它最简单**：

- 纯字节流，FatFs 不关心内容编码；
- 不需要解码器、不需要额外内存缓冲（一次读 4 KB 即可）；
- 已有 `app_command` 通道 ⇒ **验收可以完全自动化**（SWD 注入正文 → 触发保存 → 复位 → 加载比对）。

**唯一要拍板的事：编码。**  
UI 字体是 UTF-8（YMGUI），FF_CODE_PAGE=936 只影响**文件名**（GBK），不影响文件内容。  
⇒ **内容直接存 UTF-8，不做转码**。这样中文正文在 PC 上打开也不乱码。

**验收判据（整数）**：

```
① 注入正文 → 保存 → f_size == strlen(正文)
② 复位 → 加载 → 与注入内容逐字节失配 == 0
③ 中文正文（含 IME 上屏的汉字）走同一条路径仍失配 == 0
```

---

### 4.2 照片 —— ⚠ 可行，但必须先降采样

**现状**：`gallery.c` 是 3 个纯色块，没有图像。

**改造**：`f_readdir` 扫 `/YMGUI/photos` → 逐条解码 → 降采样到 142×115 →  
`YMGUI_Draw_ImgScaled` 放大显示。

#### 格式选型（决定工作量与风险）

| 格式                   | 解码途径                               | 附加 FLASH      | 附加 RAM                  | 能否流式        | 结论              |
| -------------------- | ---------------------------------- | ------------- | ----------------------- | ----------- | --------------- |
| **BMP 24/16bpp 无压缩** | 自己写（~2 KB）                         | ~2 KB         | **≈ 一行**（320×3 = 960 B） | ✅ **逐行**    | ★ **第一个做**      |
| **JPEG**             | **芯片硬件 JPEG 解码器** + DMA2D 转 RGB565 | ~8 KB（HAL 驱动） | 输入缓冲 8~20 KB + 输出缓冲     | ❌ MCU 块输出   | ★ **第二做，不用软件库** |
| PNG                  | 软件 inflate                         | +40 KB        | 32 KB 窗口                | 逐行但需 filter | ❌ 性价比最差，不做      |

**BMP 为什么第一个做**：

- **零外部依赖**，代码量 ~2 KB，不牵扯 JPEG/DMA2D/MDMA 三个外设的配置；
- **可以逐行流式**：`f_read` 一行（960 B）→ 转 RGB565 → 按 1/2 抽样写入目标缓冲 → 丢弃，  
  全程**不需要全尺寸中间缓冲**，峰值附加内存 < 1 KB；
- 顺序上注意 **BMP 行序是自下而上**（bottom-up），要反向写。

**JPEG 走硬件的两个剩余约束**（详见 §2.4）：

1. **输出缓冲照样要，且没有硬件缩放** ⇒ 要么约束源图尺寸（见下），要么 CPU 抽样降采样；
2. 输出按 MCU 块吐出，一张图要分多次 `HAL_JPEG_Decode_DMA` ⇒ 仍要控制单次耗时不超 5 ms 预算。

**源图尺寸约束（硬件解码下最省事的内存解法）**：  
既然硬解只能出原尺寸，就**让卡上的 JPEG 尺寸本身就合适**：

| 源图尺寸        | RGB565 输出    | 是否放得进 115 KB |
| ----------- | ------------ | ------------ |
| 320×240     | 153 600 B    | ❌            |
| 284×230     | 130 640 B    | ❌            |
| **240×180** | **86 400 B** | ✅            |
| **160×120** | **38 400 B** | ✅ 很宽松        |

⇒ 配图在 PC 侧预先缩到 ≤240×180 即可**完全绕开降采样**，这也是最省 CPU 的做法。

**验收判据（整数）**：

```
① 目录枚举条数 == 卡上实际图片文件数
② BMP：解码后缓冲与"主机侧按同一降采样规则算出的 RGB565"逐字节失配 == 0
③ JPEG（硬件路径）：硬解输出经 DMA2D 转出的 RGB565，与主机侧参考解码结果失配 == 0
④ 连续切换 N 张后 heap1 峰值增量 == 0（无泄漏）
⑤ 切图期间最大帧时间 ≤ 16 ms
```

### 4.3 下载 —— ⚠ 可行，但语义必须改

**现状**：`files.c` 里下载卡片的四条硬编码文案是  
`{"暂无下载内容", "浏览器尚未联网", "演示文件系统", "返回上一级"}` —— 它自己已经写明"未联网"。

板上**没有 WiFi / 以太网**，`browser.c` 也是演示态 ⇒ **"下载"这个动作在本板上不存在**。

**可行做法**：把它改成**通用文件浏览器**，映射到卡上 `/Download` 目录，  
文件由**用户在 PC 上拷进 TF 卡**。UI 文案改为"外部文件"或保留"下载"但副标题说明来源。

这样"下载"卡片和"文件浏览器"其实是**同一个东西** ——  
考虑到四个卡片本来就要共用一套目录浏览逻辑，**实现一次、四个卡片复用**是合理设计。

**验收判据（整数）**：

```
① 列出 /Download 下文件，条数与 PC 侧 `dir` 结果一致
② 点开文本文件 → 预览内容与 PC 侧前 N 字节一致（失配 0）
③ 目录为空时显示占位文案，不白屏、不 HardFault
```

### 4.4 录音 —— ❌ 硬件上不成立

见 §3.5：**板上没有 MIC、没有 codec、没有扬声器。**

`recorder.c` 现在的文案已经诚实（"开始**演示**录音"、"**未采集**声音"），  
接入 TF 卡**不会改变这一点** —— 卡只能存文件，不能凭空产生音频数据。

**唯一能做的**：把录音卡片降级成"音频文件清单"：

- `f_readdir` 扫 `/YMGUI/rec`；
- 对 `.wav` 文件**只读 44 字节头**（`f_read` 一次即可）解析出采样率/位深/时长，显示出来；
- UI 明确标注"本板无音频器件，仅显示文件信息"。

**不能假装能播放** —— 没有 DAC 通路，播不了。

**验收判据（整数）**：

```
① 清单条数 == 卡上实际文件数
② WAV 时长 == (fsize-44) / (采样率 × 通道 × 位深/8)，与 PC 侧计算结果一致（误差 0）
③ 非 WAV 文件不崩溃，标注为"不支持"
```

## 5. 共性问题与对策（四个卡片都会撞上）

### 5.1 FatFs 是阻塞的 ⇒ 必须限量 + 分帧

- **一次枚举 ≤ 32 条**，`f_readdir` 循环里超过就退出，下一帧继续（用一个静态游标）；
- 大文件读用 512 B / 4 KB 分块，每块之间让出主循环；
- ⚠ 单帧预算只剩 **≈5 ms**（16 − 10.89），`f_read` 4096 B 要 0.9~1.15 ms ⇒  
  **一帧最多读 2~4 块**，不能 while 读完整文件。

### 5.2 卡没插 / 挂载失败 ⇒ 必须降级，不能白屏

`g_fs_mount_rc != 0` 时，四个卡片都要显示"未检测到存储卡"并保留返回路径。  
现在 `files.c` 的 `file_refresh()` 直接写死文案，**没有任何失败分支** —— 这是要新增的。

### 5.3 LFN 缓冲别放栈上

`FF_USE_LFN=1`、`FF_MAX_LFN=255`、`FF_LFN_UNICODE=0` ⇒  
每个 `FILINFO` 要配一个 **255 B 的 LFN 缓冲**，加结构体本身约 30 B ≈ **285 B/条**。  
栈上开 32 条 = **9 KB**（本工程栈不大）⇒ **必须用静态缓冲或单条复用**。

> 另注：`FF_USE_FIND = 0` ⇒ `f_findfirst/f_findnext` **不可用**。  
> 目录枚举**只能用 `f_readdir`**（基础 API，不受该开关影响）。


### 5.4 不要破坏现有验收

每改一个 App 都要重跑：

```
tools/dma_check.py      # 用例② 失配 0（L3 非缓存区不能破）
tools/fs_check.py       # FatFs 挂载/写读/删除
tools/sd_check.py       # 扇区级，--repeat 3
tools/heap_peak_check.py# heap1 峰值不能逼近 204 KB
tools/ime_probe.py      # IME 3/3
```

外加 `g_fault` 全 0、A2 ramp/gram = 0。

## 7. 明确不做的事

- **不做音频录制 / 播放** —— 板上没有音频器件（§3.5），做了也是假的；
- **不引入软件 JPEG 解码库（tjpgd 等）** —— **H743 自带硬件 JPEG 编解码器**（§2.4），  
  用软件库是白花 12~~15 KB FLASH 和 3~~6 KB RAM；
- **不做 PNG** —— inflate +40 KB FLASH，性价比最差；
- **不做 `f_mkfs`** —— `FF_USE_MKFS` 已刻意关成 0，固件不该能格式化用户的卡；
- **不碰扇区 0 / 不做裸写** —— 一路只走 FatFs 文件 API；
- **不在单帧内做整文件 IO 或整图解码** —— 会打破 16 ms 帧预算（§3.3）。

## 8. 落地更新（2026-10-08，S3 已完成）

**相册 BMP 显示已落地**，但走的路与本文 §4.2 / §6-S3 的设想**不一样**，而且更好：

| | 本文初版设想 | 实际实现 |
| --- | --- | --- |
| 数据落点 | 读卡 → 解码到 RAM → 显示 | 读卡 → 解码 → **灌 W25Q128** → **XIP 直读显示** |
| 内存 | 必须先降采样（284×230 RGB565 = 130 640 B > heap1 余量 115 KB） | **零 RAM 显示**；转换期峰值 6 KB，与图尺寸无关 |
| 降采样 | 必须 | **不需要**，全尺寸也能放 |
| PC 参与 | 可选（`tools/img2rgb565.py` + 灌库） | **不需要**，固件自己完成整条链路 |

关键理由：`YMGUI_DrawImg.h` 里 `GYimg.data` 是 **`const GYpx*`** ⇒ 像素可以指向
`0x9000_0000 + offset` 的 XIP 窗口，整幅图留在 flash 里。于是"内存不够"这个问题
被换成了"怎么流式把图灌进 W25Q128"，而后者没有尺寸上限。

实现与验收见 `src/img_store.c/.h`、`docs/DEVELOPMENT_LOG.md` 的同日第四轮章节、
`tools/img_check.py`（数据判据）与 `tools/gallery_shot.py`（视觉判据）。

⚠ 由此产生一条**新的硬约束**（本文初版没有、实测踩出来的）：
`qspi_write` 只退映射不恢复，而 **indirect 模式下读 XIP 窗口会 BusFault/HardFault**
⇒ 写完必须 `qspi_enter_mmap()`，导入期间必须屏蔽一切读 XIP 的代码路径。

尚未做：S1（笔记落盘）、S2（目录浏览内核）、S6（JPEG）。JPEG 那条仍按 §2.4 的结论走 ——
硬件不做缩放，先决条件是把卡上的图预缩到 ≤240×180。
