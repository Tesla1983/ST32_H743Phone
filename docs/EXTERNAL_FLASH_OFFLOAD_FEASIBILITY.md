# 把内部 flash 的产物搬到 W25Q128 —— 可行性报告

日期：2026-10-04
问题：本板有一颗 W25Q128（16 MB，QUADSPI，memory-mapped 到 `0x9000_0000`）。
内部 flash 已用 75.15%，有什么产物可以优化到外部 flash？

> ## 决策：**本轮不做**（2026-10-04，看过本报告后）
>
> **理由：要解决的问题不存在。** 内部 flash 用了 75.15%、**还剩 509 KB**，
> 没有功能因为放不下而被挡住 —— 而本报告提出的每一项，收益都是"更多的空闲空间"，
> 代价却都是实打实的：
>
> - **A**（最大、959 KB）要拿掉"字库自愈"这份保险：一旦判据（记账头 + XIP CRC）
>   不成立就转入写入分支，而那是唯一读内部 blob 的地方；删掉后**修不回来**，
>   表现是界面中文全空白。用一份运行时保障换不需要的空间，不划算。
> - **B/C/D** 是"换指针"而不是"删冗余"，要在运行期读 QSPI。XIP 区是
>   **只读 + 非缓存 + XN**，随机访问延迟未实测；这同样是用未量化的风险换不需要的空间。
> - **E**（代码 XIP）本来就是反对项。
> - **F**（裁掉其它面板的初始化）是唯一零风险的，但只省 ~20 KB ≈ 1.3%，
>   不值得单独起一轮构建/烧录验证。
>
> **什么时候该回来重新评估**：当内部 flash 跨过 ~85%，或者出现一个"因为放不下而做不了"
> 的具体功能时。到那时本报告的分析与数字可以直接复用，不需要重新做一遍调研；
> 优先级顺序也仍然是 A → B → C/D，且 A 建议优先考虑 **A2 压缩内嵌**（保留自愈）。
>
> ⚠ **本文其余部分保留为"当时的可行性分析"，不是待办清单。**

数据来源：`build/ymgui-h743.map`（linker map，**已过 `--gc-sections`，权威**）、
`nm -S`、`src/qspi_port.h` 的布局约定、以及源码里的引用点。所有尺寸都是实测，不是估算；
估算的地方都单独标了（估算）。

## 0. 结论摘要

**内部 flash 的 88.4% 是字体/词典载荷，而这其中的 70% 运行期根本不读。**

| # | 候选 | 大小 | 占内部 flash | 运行期在用？ | 收益 | 风险 | 建议 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **A** | `gb2312_glyphs.bin`（内嵌字库载荷） | **982 016 B** | **62.3%** | **否**（运行期走 QSPI XIP） | 75% → 28.3% | 失去"空片自愈" | **首选**，收益最大 |
| **B** | `phone_font.c` 四张 ASCII 位图 | **295 260 B** | 18.7% | 是（只读位图） | 28.3% → 14.2% | 低（机制已跑通） | **第二步** |
| **C** | `pinyin_gb2312.bin`（IME 词典） | **116 350 B** | 7.4% | **是（零拷贝随机访问）** | 14.2% → 8.7% | **中：打字延迟** | 先实测延迟 |
| **D** | 引擎自带字体表（`s_font_bitmap`/`s_cjk_bitmap`/`GB2312_cps`） | 31 024 B | 2.0% | 是（含码点查表） | 8.7% → 7.2% | 同 C | 低优先 |
| **E** | 把**代码**搬到 QSPI 执行（XIP） | ~150 KB | 9.5% | 是（取指） | — | **高，且不划算** | **不做** |
| **F** | 删掉其它面板的初始化/演示字体（非"搬家"，是清理） | ~20 KB | 1.3% | 否 | 顺手 | 极低 | 顺手做 |

**一句话**：只要把 A 做掉，内部 flash 就从 **75.15% 降到 28.3%**（腾出 1.43 MB）；
A+B+C 做完可到 **8.7%**（腾出 1.86 MB）。

## 2. W25Q128 现状

16 MB = 16 777 216 B。**已用约 986 KB（6%）**：

| 区域（`src/qspi_port.h` 的布局约定，计划书 §6.4） | 规划大小 | 当前实际占用 |
| --- | ---: | --- |
| `0x000000 ~ 0x0FFFFF` 字模 | 1 MB | **982 016 B**（0xEFC00） |
| `0x00FFF000` 记账扇区（font_provision 的 magic/size/CRC） | 4 KB | 64 B |
| `0x100000 ~ 0x2FFFFF` 图片 / 壁纸常量 | 2 MB | **空** |
| `0x300000 ~ 0x5FFFFF` IME 词典载荷 | 3 MB | **空** |
| `0x600000 ~ 0xFEFFFF` 文件系统区 | ~10 MB | **空** |
| `0x000FE000` 阶段 4 擦写回环落点 | 4 KB | 验收用 |

> **架构上早就给"要搬的东西"留好了位置**：图片区（放 B）、IME 词典区（放 C）都是空的。
> 现在讨论的不是"要不要新增一个存储层"，而是"把已有的两块空区域用起来"。

## 3. 决定性事实：哪些载荷运行期根本不读

这一节是整个报告的依据，所以把引用点列全。

### 3.1 `gb2312` 字库：内部那份**是纯冗余**

运行期取字模走的是 QSPI XIP，不是内部 flash：

```c
/* third_party/YMGUI/project_Demo/phone_shell/phone_locale.c:36-47 */
#if defined(PHONE_LOCALE_XIP_BASE)
    ... (const uint8 *)(PHONE_LOCALE_XIP_BASE),   /* bitmap = QSPI XIP 基址 0x90000000 */
    NULL                                          /* glyph_read = NULL：直接用 bitmap 指针 */
```

注释原文：「库按 `bitmap + off` 取点阵，**一次拷贝都不做**」。

而内部那份 blob 在全工程里**只有一个引用点**：

```c
/* src/font_provision.c:103-104（写分支专用） */
src      = _binary_gb2312_bin_start;
src_size = (uint32_t)(_binary_gb2312_bin_end - _binary_gb2312_bin_start);
...
/* 只有需要灌库时才用： */
rc = qspi_write(src, 0u, src_size);                                    /* :143 */
hdr.crc = crc32_update(0xFFFFFFFFu, src, src_size) ^ 0xFFFFFFFFu;      /* :156 */
```

**正常启动走的是跳过分支，一个字都不读它**（跳过分支用 `crc32_of_xip()` 从 QSPI 复核）：

```c
/* src/font_provision.c:124-135 —— 头匹配就只做 XIP CRC，通过即返回 */
if ((s_force == 0) && (hdr.magic == FONT_MAGIC) && (hdr.size == src_size)) {
    if (qspi_enter_mmap() == QSPI_OK) {
        g_font_crc_calc = crc32_of_xip(0u, src_size);   /* ← 读 XIP，不读 blob */
        if (g_font_crc_calc == hdr.crc) { g_font_ok = 1; return 0; }
```

⇒ **那 982 KB 的唯一作用是"万一 QSPI 里没有/坏了，能自己灌一遍"。**
一旦 QSPI 已灌好，它就是一坨永久占着 62% 内部 flash 的死数据。
（`font_provision_set_force()` 只被定义、没有被调用过，所以 `s_force` 恒为 0。）

### 3.2 `pinyin_gb2312.bin`：**运行期真的在用**，不能删

```c
/* third_party/YMGUI/project_Demo/chinese_ime/ime_candidates.inc:184-185 */
entries[i].py = (const char*)blob + py_offset;     /* ← 指针直接指进 blob，零拷贝 */
entries[i].ch = (const char*)blob + char_offset;
```

`entries[]` 只是索引（7291 × 12 ≈ 85 KB 在 heap1），**拼音串和汉字本身仍在 blob 里原地读**。
所以这 116 KB 只能"换指针"（改到 XIP），不能删。

### 3.3 `phone_font.c` 四张位图：只读、可换指针

它们是 `const` 位图数组，经 `phone_font_regular` / `phone_font_display` 等 `GYFONT` 结构体
被文字绘制读取。引擎的字体结构**本来就支持** `bitmap = XIP基址 + 偏移` + `glyph_read = NULL`
（3.1 那条路已经跑通），所以机制是现成的。

## 4. 逐项可行性

### A. `gb2312_glyphs.bin`（982 KB，占 62.3%）—— 首选

**为什么可行**：见 3.1 —— 运行期零引用，只作一次性灌库源。

**代价（必须说清楚）**：失去"空片自愈"，而且**不止空片这一种情况**。

正常启动的判据是「记账头 magic+size 匹配 **且** XIP 逐块 CRC 匹配」。
只要这个判据不成立 —— 空白芯片、擦错扇区、QSPI 内容被破坏、CRC 计算遇上读取异常 ——
`font_provision_ensure()` 就会**转入写入分支**，而那正是唯一读内部 blob 的地方。
删掉 blob 之后，这条"修回来"的路会失败（`g_font_rc = 3`，写失败），
表现是**界面里所有中文变成空白/错字**，且无法在板上自行恢复（要用 factory 映像重烧一次）。

换个说法：现在的设计用 982 KB 内部 flash 买了一份"字库永远能自愈"的保险。
要不要继续付这份保费，是这次决策的真正问题。

首次灌库的耗时也是实打实的：**约 240 个扇区**，按工程记录的 ~45 ms/扇区擦除估算
≈ 11 s，加页编程约 **13~14 s**（估算，未实测）。

三个方案：

| 方案 | 做法 | 省下 | 保留自愈？ | 工作量 |
| --- | --- | ---: | :---: | --- |
| **A1 双映像**（推荐先做） | blob 的编入改成 CMake 选项（照 `YMGUI_DIAG` 的写法）。产线先用"factory 映像"（含 blob）灌一次 QSPI，再烧"production 映像"（不含 blob） | **982 KB** | 否（但 factory 映像在手，可随时恢复） | **小**：一个 option + 两步烧录流程 |
| **A2 压缩内嵌** | blob 压缩后内嵌（4bpp 字模大量 0，压缩率通常 40~60%），首上电解压→**分块**写 QSPI（流式，不需要大 RAM 缓冲） | 约 400~600 KB（估算） | **是** | 中：一个解压器（几百字节代码）+ 灌库变慢 |
| **A3 放 TF 卡/U 盘** | 载荷从可插拔介质读（项目正在加 SDMMC） | 982 KB | 是（需卡在位） | 中：依赖还没做完的 SDMMC/文件系统 |

> A1 的价值在于**零算法风险**：不改一个字模格式、不加解压器，只是"哪张映像上板"。
> 代价是产线多一道工序。如果一条产线只烧一遍（比如 QSPI 由外部编程器预烧），
> 那 A1 就是完全免费的 982 KB。

### B. `phone_font.c` 四张 ASCII 位图（295 KB，18.7%）—— 第二步

**做法**：把这 4 张表从 `static const` 改成 QSPI 载荷（写到规划好的图片区 `0x100000`），
`phone_font.c` 里的字体结构体改成 `bitmap = 0x90100000 + off`、`glyph_read = NULL`。
项目已有现成的搬运工具链（objcopy 打包 + `qspi_write` 灌入 + `font_provision` 的记账/CRC 范式，
照 gb2312 抄一份即可）。

**风险：低。**
- 机制与 gb2312 完全相同，已经在板上跑通；
- 这 4 张是 ASCII 位图，单字取点数比 CJK 16×16 更小、更顺序；
- 项目实测过"把 XIP 区改成可缓存，帧基准纹丝不动" ⇒ 字模读取本来就不是瓶颈。

**注意**：`phone_font.c` 在桌面上也可能被用（SDL 构建）。要保留"桌面走内嵌、板级走 XIP"的宏分支
（`phone_locale.c` 已经是这个写法，照抄）。

### C. `pinyin_gb2312.bin`（116 KB，7.4%）—— **先实测再决定**

**为什么有风险**：3.2 说了它是**零拷贝 + 运行期随机访问**。
现在它在内部 flash 上（片内总线、几百 MHz、命中成本接近 RAM），
搬到 QSPI 后每次 `entries[i].py[0]` 都要过一次 QSPI 事务；
而 XIP 区被 MPU 显式配成**只读 + 非缓存 + XN**（`BSP/MPU/mpu.c` region 0），
**没有 cache 帮忙**。候选词是按拼音前缀扫桶的，属于典型的随机小访问 —— 这正是
非缓存 XIP 最不擅长的访问模式。

**而且项目自己已经证伪过"XIP 取字模是瓶颈"这个假设**（改成可缓存后帧基准不变），
说明字模那种"每字一次连续小块读"确实不慢；但**那不是随机访问的证据**，
不能直接外推到 IME 的桶扫描。

⇒ **必须实测**：把 XIP 读的随机访问延迟量出来（例如加一个 micro.py case，
按 IME 的方式跳着读 116 KB 载荷），再决定搬不搬。布局已经预留（3 MB @ `0x300000`）。

**如果实测可接受**，改法很小：`ime_candidates.inc:212` 把 `data = _binary_ime_chars_bin_start`
改成 `data = (const uint8*)(QSPI_XIP_BASE + 0x300000)`，再加一条"把 pinyin 载荷也灌进 QSPI"的 provision。

### D. 引擎自带字体表（31 KB，2.0%）—— 低优先

`s_font_bitmap`(6 KB) / `s_cjk_bitmap`(9.4 KB) 是"回退字体"，机制同 B。
`YMGUI_GB2312_cps`(15 KB) 是**码点表**，找字形时要查 ⇒ 与 C 同类的随机访问问题。
收益只有 2%，建议放到最后，或者干脆不动。

### E. 把代码搬到 QSPI 执行 —— **不建议**

- 收益小：全部代码+杂项只有 ~182 KB（11.6%），而 A+B+C 能拿到 1.39 MB；
- 风险高：XIP 区是**非缓存**的，逐条取指性能不可接受；要跑得动必须给 XIP 开 cache，
  而这会引入 cache 维护负担（项目刚在 DMA 一致性那轮把 cache 策略固化成"不可运行期更改"）；
- 项目已经实测过"XIP 改可缓存对帧基准无收益"，说明**代码放片内是对的**。

### F. 顺手能删的死代码（~20 KB，与本主题无关但同属"省 flash"）

本板只可能是 ST7796，但 `lcd.c` 里编进了**所有**面板型号的初始化：
`lcd_ex_nt35510_reginit`(5 096 B) + `lcd_ex_nt35310_reginit`(3 380 B) + 其它型号，
以及厂商演示用的 `asc2_3216/2412/1608/1206` 字体表。
用一个宏只保留 ST7796 分支即可。**零风险、纯删除**，但只省 ~20 KB（1.3%），
属于"清理"而不是"搬家"。

## 5. 推荐路线

| 阶段 | 做什么 | 内部 flash 用量 | 累计腾出 | 前置 |
| --- | --- | ---: | ---: | --- |
| 现状 | — | 75.15%（已用 1 575 908 B） | — | — |
| **①** | **A1 双映像**（或 A2 压缩，看是否要保自愈） | **28.3%** | **959 KB** | 产线多一道工序 |
| **②** | **B 四张位图搬 QSPI** | **14.2%** | **1.22 MB** | 照 gb2312 抄一遍搬运流程 |
| **③** | 实测延迟 → 决定是否搬 **C**（+D） | **8.7%** | **1.33 MB** | 需要一次 XIP 随机读延迟实测 |
| 顺手 | F 裁掉其它面板的初始化 | 7.4% | — | 无 |

做到 ② 之后，内部 flash 只剩 ~300 KB，**腾出的空间已经超过现在总用量的一半以上**，
后续加功能基本不用再为 flash 发愁（heap1 那 30 KB 也刚回收，RAM/ROM 两头都松了）。

## 6. 需要实测 / 待确认的点（按重要性）

1. **XIP 非缓存随机读的延迟**（决定 C/D 值不值得做）——
   建议加一个 micro.py case：按 IME 桶扫描的方式跨步读 116 KB 载荷，与片内 flash 同口径对比。
2. **首次灌库的真实耗时**（现在是按 45 ms/扇区估算的 ~13 s）——
   写 `g_font_rc` + 计时即可量；这个数直接影响"要不要保留自愈能力"的取舍。
3. **A1 的产线流程可行性** —— 是否有"先烧 factory 映像灌 QSPI、再烧 production 映像"的工序条件；
   或者 QSPI 能否用外部编程器直接预烧（那样连 factory 映像都省了）。
4. **B 的 XIP 偏移与桌面构建分支** —— 确保 SDL/桌面构建仍走内嵌，别把桌面版弄坏。

## 附：本报告最容易被误读的两点

- **"字库在 QSPI 上"是对的，但内部还留着一模一样的 982 KB。**
  README 阶段 4 记的是"只读常量上 W25Q128（memory-mapped）✅ 完成"，
  容易读成"内部 flash 里没有字库了"。实际上内部那份仍占 62.3%，
  只是运行期不再读它 —— 这正是本次能腾出 1 MB 的空间来源。
- **"搬走"不等于"删掉"**：B/C/D 三类在运行期**真的会被读**，
  它们是"换指针"，不是"删除"；只有 A 是真正的冗余副本。
